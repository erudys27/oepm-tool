# Lockfile format (draft)

Status: draft — not yet implemented. `propath_order` question resolved
(2026-08-13): always recomputed, never stored — see below.

## File

`oepm.lock`, generated by `oepm install`, committed to source control.

## Purpose

Records the exact resolved version of every package (direct and
transitive) so builds are reproducible. Given PROPATH is a single, flat,
ordered, session-global list (see docs/spec/propath-generation.md), the
resolver must select exactly **one** version per package name per
project — there is no npm-style "install both" escape hatch. The lockfile
is what makes that single resolved choice explicit and stable.

## Draft shape

```json
{
  "resolved": {
    "acme.common": {
      "version": "1.0.3",
      "source": "local:///registry/acme.common/1.0.3",
      "integrity": "sha256:..."
    },
    "acme.validation": {
      "version": "1.2.0",
      "source": "local:///registry/acme.validation/1.2.0",
      "integrity": "sha256:..."
    }
  }
}
```

`propath_order` is deliberately **not** part of this shape — see below.

## Decided: propath_order is not stored

The propath generator (`oepm propath`, per
[propath-generation.md](propath-generation.md)) always recomputes ordering
from `resolved` at build/generation time; the lockfile only records what
versions were resolved, not what order they should appear on PROPATH in.
This keeps the two components decoupled and prevents a stored order from
going stale relative to the resolved graph. The `demo/exploration`
walkthrough's hand-written `oepm.lock` predates this decision and still
has a `propath_order` key — that field is now considered vestigial there,
not a model to copy.

## Open questions

- Integrity hashing scheme - needed even for the local-directory registry,
  to detect a package changing under an already-resolved version.
- Whether a version conflict between two dependencies should always be a
  hard failure (current behavior, `oepm/resolver/DependencyResolver`) or
  should support an opt-in resolution strategy — several considered
  (Gradle/Maven-style auto-pick, a Yarn/npm-style manual override field,
  encouraging a naming convention instead), see
  [version-conflict-resolution-strategies.md](../research/version-conflict-resolution-strategies.md)
  for the full comparison. Leaning: a manual-override field is a better
  fit than auto-pick if this is ever revisited, since it doesn't add
  silent-resolution risk. Not decided; current hard-fail behavior
  stands until this is revisited.
